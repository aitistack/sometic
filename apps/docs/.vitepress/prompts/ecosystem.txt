You are scaffolding with Sometic (@sometic), a portable application behavior system, not a visual UI kit.

Product facts:
- Shared controllers for UI, forms, auth, HTTP, query (server state), and document head
- System composition: @sometic/app-shell → createAppShell({ auth, http, query, head, theme, stores, forms })
- Thin adapters: React (@sometic/react), Vue (@sometic/vue), Web Components (@sometic/elements, sometic-* prefix)
- Packages are unstyled by default; consumer owns CSS, fonts, and design system
- Docs: https://sometic.dev · npm scope: @sometic · public beta

Architecture (one-way dependencies):
Consumer app → framework adapters → app-shell (composition) → features (forms, auth, http, query, theme, dom, …) → foundation (core, events, store, styling, accessibility, …)
Cores never import React/Vue/frameworks. No browser globals at import time.

State placement:
- Client/UI/app preferences → @sometic/store (kinds: ui / prefs / session)
- Server/cache data → @sometic/query (never park API lists in the store)
- Forms → @sometic/forms + @sometic/validation (draft omit for secrets; @sometic/forms/server for error maps)
- Session → @sometic/auth (+ optional @sometic/auth-* providers); session.epoch is the System clock
- Transport → @sometic/http (interceptors, auth refresh queue, epoch ledger, policy interceptor)
- SEO → @sometic/head (+ @sometic/head/seo)
- Compose System → @sometic/app-shell

Agent workflow:
1. Prefer createAppShell when wiring auth + http + query (+ optional head/theme/stores/forms)
2. Prefer subpath imports (@sometic/react/button, @sometic/react/query) for tree-shaking
3. Use Copy Prompt buttons on surface docs, or https://sometic.dev/llms.txt and /guide/agents
4. Authorize on the server; client auth helpers are UX-only
5. Wave A (React, Vue, Elements) is the production path; Wave B/C adapters are experimental

Scaffold a small app that wires createAppShell with auth + http + query + one UI control with the correct package boundaries.
