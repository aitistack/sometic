================================================================================
PRODUCT TO BUILD
================================================================================
Name: Orbit Admin
Users: platform operators managing many customer organizations (tenants).
Outcome: Tenant switcher, members table, permission matrix, approval queue, activity audit, notifications — all scoped to the active tenant.

================================================================================
NON-NEGOTIABLE RULES
================================================================================
- Active tenantId in URL and/or cookie; always include in query keys AND HTTP headers your API expects
- On tenant switch: invalidate previous tenant query keys; re-check permissions; never flash wrong-tenant data
- Permission matrix + can() are UX; server authorizes
- Approval + activity are workflow/audit engines, not a hosted multi-tenant SaaS
- Permission matrix is NOT a CE — use /data adapters or @sometic/dom
- createAppShell; page-lifetime System (no Strict Mode dispose of create-once refs); pin @sometic versions; unit + e2e; no import-time browser globals
- No Invoice Desk, playgrounds, telemetry, invented packages

================================================================================
REQUIRED PACKAGES
================================================================================
@sometic/app-shell, @sometic/auth (+ adapter), @sometic/http, @sometic/query,
@sometic/data-table, @sometic/approval, @sometic/activity, @sometic/notifications,
framework /data (PermissionMatrix, DataTable), /overlay (Dialog)

================================================================================
DOMAIN STUBS
================================================================================
Tenant: { id, name, slug }
Member: { id, tenantId, email, role, status }
RolePermission: matrix of role × action
ApprovalCase: { id, tenantId, type: "invite"|"elevate", state, payload }
ActivityEvent: { id, tenantId, actorId, message, createdAt }

Actions: members:read, members:invite, roles:edit, approvals:decide

Mock API must reject cross-tenant access even if client lies about tenantId.

================================================================================
SCREENS
================================================================================
1. Sign-in
2. Shell with tenant switcher
3. Members data-table for active tenant
4. Roles: Permission matrix editor (save via mutation)
5. Approvals queue: approve/reject with confirm Dialog
6. Activity feed filtered by tenant
7. Notifications for new approval assignments

================================================================================
WIRING RECIPE
================================================================================
1. App Shell auth/http/query
2. After /me, load tenants list; set active tenant
3. http default headers / interceptor inject X-Tenant-Id (or your scheme)
4. Query keys ALWAYS include tenantId: ["t", tenantId, "members"]
5. createPermissionController from capabilities for active tenant
6. approval controller for invite/elevate flows; activity append after decisions
7. On switchTenant(next): navigate, clear old keys, refetch

================================================================================
IMPLEMENTATION STEPS
================================================================================
1. Vite + mocks that enforce tenant header
2. System + auth + tenant context
3. Members table
4. Permission matrix page
5. Approvals + dialogs + activity writes
6. Notifications hookup
7. CSS densify; README documents tenancy model and “no @sometic/tenant”

================================================================================
ACCEPTANCE CRITERIA
================================================================================
[ ] Switching tenants changes table data without showing previous tenant rows
[ ] Removing tenant header on API returns 403 in mock
[ ] Matrix edits require roles:edit permission in UI and API
[ ] Approval decision creates activity event
[ ] Notifications appear for assignees
[ ] dispose safe on remount
