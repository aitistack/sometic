================================================================================
PRODUCT TO BUILD
================================================================================
Name: Deskline Support
Users: support agents triaging tickets, updating status, viewing activity, receiving assignments.
Outcome: Queue + detail + create/update forms + dialogs/toasts + notifications + activity timeline.

================================================================================
NON-NEGOTIABLE RULES
================================================================================
- Ticket lists/detail in @sometic/query; status machine on the SERVER
- Forms for create/update; Dialog confirm for resolve/close; Toast for success
- @sometic/activity for audit timeline; @sometic/notifications for assignments
- Realtime optional: bring your own websocket/SSE → invalidate query (no @sometic/realtime)
- createAppShell; dispose; no import-time browser globals
- Unstyled; priority colors in consumer CSS
- No telemetry, playgrounds, Invoice Desk

================================================================================
REQUIRED PACKAGES
================================================================================
@sometic/app-shell, @sometic/auth, @sometic/http, @sometic/query,
@sometic/forms, @sometic/validation, @sometic/notifications, @sometic/activity,
framework /field, /overlay (Dialog, Toast), /button

================================================================================
REPO LAYOUT
================================================================================

  tickets/
    queue-page.tsx

    status.ts                 // client labels only; server is source of truth

README.md                     // explicit “not Invoice Desk”

================================================================================
DOMAIN STUBS
================================================================================
Ticket: { id, subject, description, priority: "low"|"med"|"high", status: "open"|"pending"|"resolved", assigneeId?, updatedAt }
ActivityEvent: { id, ticketId, message, actorId, createdAt }

API:
- GET /tickets?status=&priority=
- GET /tickets/:id
- POST /tickets
- PATCH /tickets/:id
- GET /tickets/:id/activity
- notifications endpoints

================================================================================
SCREENS
================================================================================
1. Sign-in
2. Queue with filters
3. Split view / route detail with activity timeline
4. Create ticket form
5. Resolve flow: confirm Dialog → mutation → Toast → activity entry
6. Notification center for assignments

================================================================================
WIRING RECIPE
================================================================================
1. App Shell
2. Query keys: ["tickets", filters], ["tickets", id], ["tickets", id, "activity"]
3. Mutations invalidate list + detail + activity
4. After status change accepted by API, append/read activity
5. Assignment events → notifications inbox

================================================================================
IMPLEMENTATION STEPS
================================================================================
1. Vite + mock API with status transition rules
2. System + auth
3. Queue + filters
4. Detail + forms
5. Dialog/toast flows
6. Activity + notifications
7. Optional fake SSE button that invalidates keys (document as demo)
8. README honesty section

================================================================================
ACCEPTANCE CRITERIA
================================================================================
[ ] Create ticket appears in queue via query invalidation
[ ] Illegal status transition rejected by mock API and shown in form errors
[ ] Resolve requires confirmation dialog
[ ] Activity shows decision after success
[ ] No Invoice Desk naming or dependencies
[ ] dispose safe
